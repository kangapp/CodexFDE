长期目标是：结合 AI 稳定产出高质量 Spec，使项目持续迭代有据可查、减少目标偏差，并逐步积累和复用经验。

本次只交付本地 Python CLI 工作台 V0.1：能够初始化、登记项目、创建任务、追加运行记录、查询状态。它保存并关联当时要求和实际输出，为本人核对项目目标、当前进度与历史总结提供材料。重启后仍应能查回；错误操作不得破坏已有记录。

非目标：自动生成或评价 Spec、自动调用 Codex、自动采集全部执行过程、自动总结或召回经验、自动判断项目是否跑偏、网页/HTTP API、FlowERP 接入。保存记录不证明经验已经有效复用，程序判定材料完整不替代本人审核。

## 2. 使用过程与对象

1. 本人确认 Spec，后续另行准备测试、采集有效红灯、授权实现并正式复验。
2. 复验后初始化工作台，登记个人研发工作台项目，创建本次建设任务。
3. 任务创建时保存本 Spec 与原始问题的全文副本；以后源文件改变，已保存副本保持不变。
4. 将本次实际红灯、Diff、绿灯记录分别追加到同一任务，失败退出码保持原值。
5. 查询任务、快照和历次记录；本人据此核对最终目标、进度和总结，发现目标偏差先纠正或补充材料。

| 对象 | 必需信息与归属 |
|---|---|
| 工作台 | 名称、所有者（本人课程编号），独立本地数据目录 |
| 项目 | 稳定项目编号、名称、绝对代码目录、建设目的 |
| 任务 | 稳定任务编号、已登记项目编号、需求编号、任务要求、操作者、Spec 与问题源路径及创建时全文快照 |
| 运行记录 | 所属任务编号、阶段、命令文本、输出源路径与导入时内容快照、原退出码、带时区观察时间 |

一个项目对应多项任务，一项任务对应多次运行记录。任务编号在本工作台内唯一。查询使用已存快照，不能临时重新读取源文件代替历史内容。

## 3. CLI 输入、输出与失败行为

入口统一为 `python -X utf8 -m workbench.cli <子命令>`。五个命令均接受 `--runtime-dir`，本次运行统一显式指定 `.runtime/course/L01-workbench`，默认值也采用此目录。输出使用可解析的 JSON；业务成功退出码为 0，业务拒绝或查询条件不满足为 1，命令参数语法错误由现有 argparse 返回 2。

成功结果包含 `ok: true` 与本次保存或读取的对象；业务失败包含 `ok: false` 与可解释的原因。所有结果如实说明 `flowerp_connected: false`。新增输出字段或数据库内部表结构不作为本次额外产品能力。

| 命令 | 输入参数 | 成功时应返回及保存 | 失败行为与操作后状态 |
|---|---|---|---|
| `workbench-init` | `--name`、`--owner` | 创建独立 `workbench.db`，返回与输入一致的工作台身份 | 名称或所有者为空则拒绝；已有工作台时拒绝重复初始化，保留身份及全部数据 |
| `workbench-project-add` | `--project-id`、`--name`、`--path`、`--purpose` | 保存项目身份和目的，路径解析为绝对目录；返回所登记项目 | 未初始化、必需文本为空、目录不存在或项目编号重复时拒绝，已有项目和任务不变 |
| `workbench-task-create` | `--project-id`、`--task-id`、`--requirement-id`、`--request`、`--actor`、`--spec-file`、`--problem-file` | 在已有项目下创建任务，读取并保存两个 UTF-8 文档的全文快照，返回任务及归属 | 项目不存在、任务编号重复、必需文本为空或文档不可读取时拒绝；没有孤立任务或半条任务，原任务、快照与记录不变 |
| `workbench-evidence-add` | `--task-id`、`--phase`、`--command-text`、`--output-file`、`--returncode`、`--observed-at` | 追加记录并保存输出快照，返回本次记录与所属任务；不执行命令文本 | 任务不存在、输出不可读取、时间不能解析为带时区时间时拒绝，无新残留记录，已有记录不变 |
| `workbench-status` | 可选 `--require-project`、`--require-task`、`--require-red-green-evidence` | 只读返回工作台身份、项目、任务、快照、运行记录及缺失项，满足本次要求时退出 0 | 未初始化或指定对象不存在、对象归属不符、所要求证据不完整时退出 1；不创建数据库、不初始化、不改变记录 |

运行记录阶段为 `red`、`diff`、`green`、`observation`，与现有采集工具一致。`--returncode` 接受实际整数退出码；导入一条非零退出码记录仍可成功退出 0，表示“导入成功”，不得把记录内退出码改为 0。

无条件状态查询展示已有材料，不要求必须具备红—Diff—绿链；带 `--require-red-green-evidence` 时，必须明确指定 `--require-task`，针对该任务检查完整性。同时指定项目和任务时，任务必须归属指定项目。

状态结果至少明确给出 `ok`、`evidence_complete`、`acceptance`、`flowerp_connected` 和缺失项；展示的任务能查到创建时两个全文快照及各条运行记录的命令、输出、退出码和观察时间。`acceptance` 始终为 `pending_human_review`，五个命令均不自动签收任务。

## 4. 记录完整性与失败语义

- 有效链属于同一任务，包含非零退出码的 red、退出码为 0 的 diff、退出码为 0 的 green。
- red 与 green 的命令文本必须一致；课程采集工具提供的是序列化后的实际命令参数。不能用另一条测试命令的成功覆盖本条失败。
- 按带时区时间比较，必须满足 `red < diff < green`，以实际观察时间判断，不能用导入先后代替。
- 同一验收命令在 green 后又有更晚的非零运行记录时，旧 green 不能继续证明当前通过，完整性应报告未满足。查询其他对象失败的不同命令不推翻本任务已有验收链。
- 缺少有效链时，在缺失项中包含 `same_command_red_diff_green_missing`；指定任务不存在时包含 `required_task_missing`；指定项目不存在或任务归属不符时给出明确原因。
- `evidence_complete: true` 只证明上述记录关系成立。有效红灯是否发现目标能力缺失、Diff 是否在范围内、测试是否覆盖需求，仍需本人检查。
- 失败记录按原样保留；后续成功不覆盖失败。所有被拒绝的请求保留原任务数量、项目归属、快照及记录；查询始终只读。
